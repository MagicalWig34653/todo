# Todolino

Todolino is the user's task and project board. The MCP server `todolino` (tools such as `get_manual`, `get_command_center`, `post_progress`, `record_sync`) is provided by this plugin. Its tools appear as `mcp__plugin_todolino_todolino__<tool>`.

0. Tool schemas are deferred: a direct call fails with `invalid_arguments` until the tool is loaded. The SessionStart hook prints the ready line; run it once per session with ToolSearch (other tools: ToolSearch with their name): `select:mcp__plugin_todolino_todolino__post_progress,mcp__plugin_todolino_todolino__claim_task,mcp__plugin_todolino_todolino__create_task,mcp__plugin_todolino_todolino__ask_question,mcp__plugin_todolino_todolino__request_review,mcp__plugin_todolino_todolino__list_tasks,mcp__plugin_todolino_todolino__get_command_center,mcp__plugin_todolino_todolino__record_sync,mcp__plugin_todolino_todolino__get_sync_status`
1. Call `get_manual` once per session and follow it; it is the authoritative description of the tools and the workflow. The section "Project onboarding and keeping Todolino current" defines the routine below.
2. Find the project: read `.todolino.json` in the repository root (`projectID`), otherwise `find_project_by_repository` with the git remote. Never create a second project for a repository that already has one.
3. Mandatory rules for every session in a bound repository. Use the board while you work; calling only `record_sync` at the end is a violation.
   - Current project: the `projectID` from `.todolino.json` is the only project you work on. One login covers all projects of the user, so ALWAYS pass it as `projectID` to `get_command_center`, `list_open_questions` and `list_pending_reviews` (answers name `currentProject`; the list tools answer `{currentProject, hint?, items}`). Never claim, edit, mention, summarise or offer tasks, questions or reviews of other projects (`foreignProject: true`, other `projectName`), not even as a suggestion. Use `scope: "account"` only when the user explicitly asks for an overview of all projects.
   - Start: `get_sync_status`, `get_project_structure` (the agent brief overrides your defaults), `get_command_center {projectID}`, `list_open_questions {projectID, includeAnswered: true}`, `list_pending_reviews {projectID}`. Handle answered questions, requested changes and tasks you already claimed first. If the sync state is `stale` or `never`, reconcile first (skill `todolino:sync`).
   - Overdue work: check `get_command_center.summary.overdue` (visible unfinished tasks, including backlog/subtasks). Cards keep `dueDate` (own planning.dueAt) and `nextDue` (earliest unfinished own/subtask dueAt), also in compact mode. Use `list_tasks {projectID, overdue: true}` for the overdue tasks; completed tasks never count.
   - Before any work: look for the matching task (`list_tasks`, command center, `list_plan_keys`); none: `create_task` (no duplicates). Then `claim_task`.
   - After every finished sub-step and every commit: `post_progress` (what is done, what is next). The Stop hook reminds if a session changed files without any board call.
   - Decisions the user must make: `ask_question` on the task (`blocking: true` if work depends on it) instead of asking only in chat. Read the answer later with `list_open_questions`.
   - Finished and the user has something to look at or decide (a visible result to try, a risk, a rollout or merge decision): `request_review`, and say in one bullet what to look at. Finished but nothing for the user to check (internal change, tests green, commit done): NO review, only `post_progress` (percent 100, commit hash and numbers there). Never mark your own work done; open the question "can this be closed?" with `ask_question` only if it is unclear.
   - Chat: tasks, questions and reviews each have a chat. At session start and after each step read new messages from people (`list_comments` with `authorKind: "person"` and `since`, plus `questionID`/`reviewID` for those cards, or `wait_for_events` hint `comment`) and answer with `add_comment`.
   - Attachments from people: a file added to a task, question or review shows up in `list_comments` as an entry with `kind: "attachment"` and `attachments: [{id, filename, mediaType, size}]` (files without a chat entry come as one trailing `attachments_note`). To look at an image or PDF: call `get_attachment_download {id}` (5-minute signed URL, never post it on the board), run `${CLAUDE_PLUGIN_ROOT}/scripts/fetch-attachment.sh "<url>" "<scratch dir>"`, then `Read` the printed path. `read_attachment` with `preview: true` only inlines tiny images (up to 45000 bytes); bigger ones return `previewOmitted: "preview_unavailable"`.
   - Writing style for everything people read on the board (reviews, questions, progress, comments, task descriptions): short and in bullet points. The headline is the task title, not the text. `request_review`: one sentence of result, then at most 4 bullets (new, checked with numbers, what to look at, open). `ask_question`: the situation in one or two lines, 2 to 4 concrete options, your recommendation first. `post_progress`: one or two sentences. Lists of findings go into the task description or subtasks, not into progress notes. No file lists, hashes or repeated titles.
   - Large actions (deleting, revoking shares, role changes for strangers, deleting columns or comments): the tool answers `confirmation_required` and the person confirms in the PWA. Do not retry or work around it; mention it in `post_progress` and continue with other work (`list_action_requests` shows the state).
   - Spawned agents: the main session creates and names the task, puts its ID in the agent prompt, the agent reports with `post_progress` itself, the main session requests the review.
   - Codex jobs (companion, Codex sandbox) and other sandboxed workers cannot call Todolino tools. The Claude session that started the job is the wrapper: it reads the job result and reports with `post_progress` (or `add_comment`) on the job's behalf, with `agentName` like `codex@<topic>` (for example `codex@review-hooks`) and the job in the note ("Codex job done: ..."). Questions of the job become `ask_question` by the wrapper. Do not leave Codex work invisible on the board. The Stop hook counts board calls of the main session and of its subagents, so the wrapper's `post_progress` satisfies it.
   - After a blocking `ask_question`: at most a few rounds of `wait_for_events` (pass the returned token as `since`), then `get_question`; if still open, end normally.
   - End: bring statuses up to date and call `record_sync {projectID, summary, repoRef}`.
4. Not yet set up? Offer the skill `todolino:setup`; do not set a repository up without the user asking.
5. If the Todolino tools are missing or return an authorisation error (`insufficient_scope`), tell the user to run `/mcp` and authenticate "todolino" again: new tools bring new scopes, and an existing connection only gets them after reconnecting. Do not work around it.
6. The tool set grows (board, sharing, teams, runs, settings, admin read). `get_manual` lists every tool with its scope; do not rely on a fixed list from memory.
